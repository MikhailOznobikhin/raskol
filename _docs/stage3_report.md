# Stage 3-PREP — Почему изогнутые стены и сводчатый потолок получились неправильно

Дата: 2026-10-29. Статус: **только анализ**, код и сцены не изменялись.
Изменён ровно один файл — этот отчёт (`res://_docs/stage3_report.md`).

Инструменты измерения (воспроизводимо, ничего не пишет на диск):

```bash
PY="$USERPROFILE/.dsh/dsh-runtimes/dsh-primary-runtime/dependencies/python/python.exe"
"$PY" src/build_dungeon_kit.py --analyze      # габариты и срезы модулей набора
# прямая разборка GLB (JSON-чанк + accessor'ы) — профиль, UV-плотность, наличие UV2
```

## 0. Короткий вывод (TL;DR)

1. **Свода нет вообще, а не «свод неправильный».** Набор `dungeon_kit.glb` — это не «стена + свод»,
   а **1.9 м толстая вырезка стены из сводчатого зала**: у неё сверху есть только *плечо* свода
   (пологая дуга от y=4.84 у лицевой кладки до y=3.85 у заднего среза), которая обрывается
   плоским задним торцом. Полного свода (полуцилиндра/арки через пролёт) в наборе нет ни в одном меше.
2. **Генератор эти модули стен не использует.** `_build_walls()` → `_build_walls_plain()` строит
   `BoxMesh(2, 1, 2)`, растянутый по Y до 4.944 м, с материалом из `assets/tex3d/stone_wall_*`.
   То есть стены — это вертикальные коробки, а не кладка из набора. Кривизне взяться неоткуда.
3. **Потолок принудительно плоский.** `_shapes()` записывает `ceil_h = WALL_H` в каждую клетку
   («Высота потолка едина»), `_build_ceiling()` строит heightfield из этих высот → одна плоскость
   на 5060 м². Плюс у меша потолка **вообще нет UV** (`set_uv` не вызывается ни разу) — его спасает
   только встроенный трипланар `StandardMaterial3D`.
4. **Главная техническая причина «песка» на потолке и «разного масштаба кирпича» — тексельная
   плотность, которая гуляет в 15 раз** (134 px/m на арках набора … 2048 px/m на потолке) при цели
   ±25%. Подробности и таблица — раздел 3.
5. **Реальная кривизна в уровне есть только в двух местах:** 29 арочных проёмов (меш набора) и
   цилиндрические опоры. Именно на опорах видно «зализанные/скошенные» кирпичи: трипланар
   смешивает две проекции на косых нормалях цилиндра (§2.3, пункт «shear»).

Рекомендация: **Вариант B+** (процедурный свод + честные arc-length UV + отдельный материал для
свода и колонн), а не покупка нового кита. Причины — раздел 7, разбивка работ — раздел 5.

### 1.3 Профиль «свода» — что на самом деле лежит в наборе

Замер по вершинам `wall_4m` (после пересборки, z=0 — плоскость лицевой кладки, z>0 — в толщу):

| z, м | y_max | y_min | средняя нормаль |
|---|---|---|---|
| −0.10…0.10 | 4.84 | 4.68 | (−0.01, −0.66, −0.75) |
| 0.10…0.30 | 4.80 | 4.64 | (0.00, −0.96, −0.27) |
| 0.50…0.70 | 4.69 | 4.46 | (0.00, −0.89, −0.45) |
| 0.90…1.10 | 4.47 | 4.21 | (0.01, −0.78, −0.62) |
| 1.30…1.50 | 4.10 | 3.89 | (0.00, −0.75, −0.66) |
| 1.50…1.70 | 3.95 | −0.01 | (0.00, −0.28, −0.96) |
| 1.70…1.90 | 3.85 | 0.32 | (0.00, −0.01, −1.00) |

Читается так: лицевая кладка стоит вертикально на z≈0 и высотой 4.84 м; от её верха внутрь
**толщи** уходит пологая дуга, опускающаяся до 3.85 м на z≈1.6, а за ней — **плоский задний торец**
(нормаль ровно −Z) до z≈1.9. То есть это *плечо* (пята) свода, вырезанное из большого зала;
продолжения дуги (самого свода) в меше нет. `arch_2m` имеет **тот же профиль** с точностью ±0.02 м.

Вывод шага 1: **набор физически не содержит сводчатого потолка.** Что бы генератор ни делал, собрать
из этих мешей «стены, переходящие в свод» нельзя — максимум «стены с плечом и плоский потолок над ним».

### 2.2 Точное место, где должна была случиться кривизна

Цепочка из пяти конкретных мест:

1. `src/build_dungeon_kit.py:426–448` — из исходной стены вырезается модуль 4×4.86×1.9 м и
   сохраняется плечо свода. Здесь кривизна **последний раз была корректной** (плотность UV на дуге
   держится ±13%: p10 0.0602, p90 0.0790 uv/m), но самого свода в меше нет.
2. `scripts/dungeon.gd:368–421` `_shapes()` — `ceil_h[y][x] = WALL_H` для всех клеток, комментарий
   прямо говорит: «Высота потолка едина: стены сохраняют прямой вертикальный профиль». Любая
   задумка свода уничтожается здесь.
3. `scripts/dungeon.gd:750–775` `_build_walls()` → `_build_walls_plain()` — **модули стен набора не
   используются вообще**, вместо них масштабированные боксы. Плечо свода пропадает.
4. `scripts/dungeon.gd:643–681` `_build_ceiling()` — heightfield из плоских высот → плоскость;
   UV не задаются, материал спасает трипланар.
5. `scripts/dungeon.gd:776–803` `_build_arches()` и `1652` `_arched_doorway()` — единственные места,
   где меш набора с плечом свода реально попадает в кадр: 29 проёмов + декор. Плечо торчит в зал на
   1.9–2.15 м и **обрывается плоским торцом** ровно там, где должен начинаться свод.

### 2.3 Причины конкретных артефактов

**«Кирпичи растянуты и скошены там, где стены изгибаются»**
Единственная изогнутая геометрия в уровне — цилиндрические опоры (`_build_piers`, `CylinderMesh`),
и они используют `mat_wall` = `stone_triplanar.gdshader`. В шейдере вес проекции
`vec3 aw = pow(abs(wn), vec3(6.0)); aw /= ...` — на грани бокса одна ось даёт вес 1.0 и курсы
идеально горизонтальны, а **на цилиндре нормаль непрерывно проходит через 45°**, где смешиваются
две проекции с разными U (`uvx = (world.z, −world.y)`, `uvz = (world.x, −world.y)`). Один и тот же
курс кладки оказывается в двух разных местах текстуры → кирпичи «веером» и с двоением; вдобавок
`cx/cy/cz` (ручной базис для карты нормалей) усредняется по тем же весам → рельеф «плывёт».
Видно на `tools/shot_3d_vault.png` (левая колонна: курсы расходятся веером) и на
`tools/shot_3d_cistern.png` (колонна в правой части читается как оранжевая «наждачка», кирпич
рассыпается в шум).

**«Масштаб кирпича отличается у соседних стен»**
Не «соседние стены», а разные материалы рядом: стена-бокс = `stone_wall` 1024 px × `uv_scale 0.4` →
**410 px/m** (плитка 2.5 м), а проём набора = собственный атлас 2048 px с UV пака 0.065 uv/m →
**134 px/m** (плитка 15.3 м). Разница **3.1×**; а с кирпичным потолком (2048 px/m) та же арка
расходится уже в **15×**. Именно это и видно в кадре: кирпич двери заметно крупнее, чем у стены, и
несопоставим с «песком» на потолке.

Поправка (см. §11): в первой редакции отчёта здесь стояло `uv_scale 1.5 → 1536 px/m` — это ошибка
чтения сигнатуры `_make_stone(tex, tint, rough, uv, nscale)`. У `mat_wall` четвертый аргумент `uv`
равен 0.4, а не 1.5 (1.5 — это `nscale`). Замеры §3 и вывод про разброс 15× от этого не меняются.

**«Текстура двери растянута»**
`_arched_doorway()` (строка 1652) ставит меш `arch_2m` со смещением **в мировых координатах**
`cell_center + Vector3(0, 0, -1.07)` — без учёта нормали стены. Для стены, идущей по Z, проём
сдвигается поперёк себя, садится на четверть в кладку или в зал, и его лицевая кладка видна под
скользящим углом. Плюс тот же 134 px/m: при 2048 атласе и UV 0.065 uv/m кирпич на двери в 3 раза
крупнее, чем у стены (410 px/m), и на 2-метровом проёме выглядит растянутым.

**«Потолок — плоская бежевая шумная текстура, похожая на песок»**
`mat_ceil` = `_brick_material(1.0)` → `brickwalls_basecolor.jpg` 2048 px, `uv1_scale = 1.0`,
`uv1_triplanar = true` (проверено по докам 4.4: у `BaseMaterial3D` флаг `uv1_world_triplanar`
по умолчанию `false`, но меш потолка стоит с identity-трансформом, поэтому local == world).
Плотность **2048 px/m** → один кирпичный ряд ≈ 3 см; с 3–8 м мип-уровни усредняют атлас до
равномерного бежевого шума. Дополнительно: `set_uv()` не вызывается, то есть **у меша нет UV вообще**
и потолок держится исключительно на трипланаре — материал без трипланара (или любой будущий
шейдер) даст заливку одним цветом. `st.set_color(Color(0.95, 0.92, 0.86))` тоже не работает:
`mat_brick` не включает `vertex_color_use_as_albedo`, а `_multimesh()` дублирует материал и включает
этот флаг только для MultiMesh.

**«Бледно-серые блочные накладки, похожие на плейсхолдер»**
`mat_cap` — `_make_stone("stone_wall", Color(0.66, 0.6, 0.54), 0.85, 0.9, 1.1)`: та же текстура, что
у стен, но с серым тинтом и **другой плотностью (922 px/m против 410)**. Единственный реальный
потребитель сейчас — подставка факела (строка 1768); арки-рёбра
`_build_ribs()` (строка 683), где `mat_cap` применялся массово, **не вызываются ни разу** (мёртвый код). То есть серые
«накладки» в кадре — это, по большей части, серый тинт `mat_cap` на мелких деталях + пересвет
боксов стен камерным `OmniLight3D` (видно на `tools/shot_3d_wall.png`: стена в упор — крупные
бледные плиты «под бетон»).

**Жёсткая линия стена/потолок**
Стены-боксы имеют высоту `wtop = WALL_H + 0.1 = 4.944`, потолок — плоскость на `WALL_H = 4.844`
(и он кроет и клетки стен). Переход — чистые 90° без карниза/гуська; в кадре это прямая полоса,
над которой начинается уже другой материал с другим масштабом.

## 3. Шаг 3. Тексельная плотность

Формула: `px/m = ширина_текстуры_px × uv_на_метр`. Для трипланара `uv_scale` и есть uv/м.
Для мешей набора `uv/м` измерена по треугольникам (медиана `|Δuv| / |Δпозиция|`).

| № | Поверхность | Текстура | px | UV-масштаб | px/m | Плитка, м |
|---|---|---|---|---|---|---|
| 1 | Стены-боксы (и стволы колонн) | `stone_wall_albedo.png` | 1024 | world triplanar, `uv_scale 0.4` | **410** | 2.50 |
| 2 | Плинт/мелкие детали, `mat_cap` | `stone_wall_albedo.png` | 1024 | 0.9 | **922** | 1.11 |
| 3 | Потолок и «кирпичные» пропы | `brickwalls_basecolor.jpg` | 2048 | `uv1_scale 1.0`, трипланар | **2048** | 1.00 |
| 4 | Пол `floor_4m` | `tile_floor_basecolor.jpg` | 2048 | UV пака, 0.1691 uv/m | **346** | 5.91 |
| 5 | Заплатка `dirt` | `sand_basecolor.jpg` | 2048 | UV пака, 0.257 uv/m | **527** | 3.89 |
| 6 | Проём `arch_2m` | `brickwalls_basecolor.jpg` | 2048 | UV пака, 0.0654 uv/m | **134** | 15.29 |

**Разброс: 134 … 2048 px/m = 15.3×.** При цели «все поверхности в пределах ±25% от одного значения»
(рекомендуемое 512 px/m для 2K на 4-метровых плитках) это расхождение в 15 раз.

Что даёт приведение к 512 px/m:

| Поверхность | Сейчас px/m | Множитель | Как править (Stage 3) |
|---|---|---|---|
| Стены-боксы | 410 | 1.25 | `mat_wall` `uv_scale` 0.4 → **0.5** |
| `mat_cap` | 922 | 0.55 | `uv_scale` 0.9 → **0.5** |
| Потолок/пропы `mat_brick` | 2048 | 0.25 | `_brick_material()` `uv1_scale` 1.0 → **0.25** |
| Пол `floor_4m` | 346 | 1.48 | `uv1_scale` на glTF-материале **1.48** (или пере-UV-exact в `build_modules`) |
| `dirt` | 527 | 0.97 | оставить |
| `arch_2m` | 134 | **3.82** | `uv1_scale` 3.8 на glTF-материале (или масштабировать UV при пересборке) |
| Пол (fallback `mat_floor`) | 1024 × 0.45 = 461 | 1.11 | `uv_scale` 0.45 → **0.5** |

Важно: у `stone_wall_albedo.png` всего 1024 px. При 512 px/m плитка = 2 м — на 4.9-метровой стене это

уже есть, `macro_strength`), либо берём 1024 px/m для стен и 512 для остального (±25% не выдержать,
но разрыв падает с 15× до 4×).

## 4. OPTION A — пересобрать стены/потолки модульными мешами с готовыми арками и сводами

Суть: уровень строится из модулей кита (стена 4 м, стена с переходом в свод, сводчатый потолок
коридора, плоский/рёберный потолок зала, арка/проём, столб, угол внутренний/наружный, плита пола,
лестница, плинтус), а генератор только расставляет `Transform3D`.

**Что есть в текущем паке:** прямые стены (с плечом), проёмы, углы, пол, грязь, факел, сундук.
**Чего нет (и без чего A не собирается):** свод/арка через пролёт, потолочные панели, рёбра,
столбы, плинтус/карниз, лестницы, UV2. То есть **A = новый пак** (или доп. моделирование ~10–15 мешей).

Объём работ по уровню (замеры выше):

| Позиция | Кол-во | Комментарий |
|---|---|---|
| Обнажённые грани стен | 584 × 2 м = 1168 пог. м, 5658 м² | при модуле 4 м → **292** экземпляра, при 2 м → **584** |
| Проёмы/арки | 29 | сейчас частично закрыты `arch_2m` |
| Углы/торцы стен | ориентировочно 180–220 | каждый торец 2-метрового выступа |
| Сводчатый потолок коридоров | ≈ 1168 пог. м → 292 модуля по 4 м | только если планировка станет коридорной |
| Плоский/рёберный потолок залов | ≈ 5060 − площадь сводов ≈ 3000 м² | панели 4×4 м → ~190 шт. |
| **Пере-авторинг `m1.txt`** | 78×46 клеток | **обязателен**: сводчатый модуль задаёт ширину пролёта |

Оценка: адаптер набора + переписывание `_build_walls/_build_ceiling/_build_arches` — **3–4 дня**;
пере-авторинг планировки под пролёты (сейчас одна пещера 5060 м²) — **1–2 дня**; калибровка
плотности/света/производительности — **1–2 дня**; поиск/покупка пака и фиксация лицензии — **0.5 дня**.
**Итого ≈ 6–9 рабочих дней** + стоимость пака.

Производительность — отдельный риск: `wall_4m` весит 6025 трис (≈1500 трис/м). 1168 пог. м → **~1.75 M
трис** только на стены, плюс своды и потолки. Для GTX 1660 это верхняя граница; понадобятся LOD или
2-метровые модули с меньшей триангуляцией.

Плюсы: настоящая геометрия свода, кладка идёт по дуге, всё в едином стиле; арки/углы перестают быть
«приклеенными»; можно один раз запечь UV2 и получить лайтмапы.
Минусы: новый пак (деньги + лицензия), полный пере-авторинг уровня, риск по FPS, срок 2 недели,
и вся ранее настроенная логика (`m1.txt`, пропы, триггеры, торчи, туман) требует пере-проверки.

## 5. OPTION B — оставить текущую геометрию, исправить UV и перейти на world-space трипланар

Суть: стены остаются боксами, но (1) свод добавляется **процедурно** — `ceil_h` перестаёт быть
константой, потолок строится как развёртка профиля (полуцилиндр/пологая арка на пролёт) с
**arc-length UV** (`u` — расстояние вдоль пролёта, `v` — длина дуги); (2) свод и колонны получают
**свой материал без трипланара**; (3) тексельная плотность приводится к 512 px/m (таблица §3);
(4) на стык стена/потолок добавляется карниз-гусёк из тех же материалов.

Конкретные правки:

| # | Место | Что делать | Оценка |
|---|---|---|---|
| B1 | `_materials()` | `uv_scale` стен 0.4 → 0.5, `mat_cap` 0.9 → 0.5, `_brick_material` 1.0 → 0.25; `uv1_scale` на glTF-материалах пола (1.48) и арок (3.8) | 0.5 дня |
| B2 | `_shapes()` + `_build_ceiling()` | `ceil_h` = функция пролёта: `h = WALL_H − r(1 − cos θ)` для клеток у стены; `_build_ceiling` строит ленту профиля (8–12 сегментов) вместо клеточного heightfield; `st.set_uv()` с arc-length V | 1.5–2 дня |
| B3 | новый `vault_triplanar`/`vault_uv` материал | для свода и колонн — **не** world-трипланар: UV из B2 (свод) и цилиндрическая развёртка (колонны, `CylinderMesh` уже с UV) | 0.5–1 день |
| B4 | `_build_walls_plain()` | высота бокса = низ свода (не `WALL_H + 0.1`), сверху карниз-бокс 0.12×0.18 м тем же материалом | 0.5 дня |
| B5 | `_build_arches` / `_arched_doorway` | посадить декор по нормали стены (`_face_xform`), а не мировым `−1.07 Z`; масштаб UV арок 3.8 | 0.25 дня |

**Итого ≈ 3.25–4.25 дня**, без покупок, без пере-авторинга `m1.txt`, без риска для логики и FPS
(геометрия добавляет ~2–4 k трис на 1168 пог. м, на порядок меньше варианта A).

Где B всё равно будет выглядеть плохо (честно):

* **Трипланар на своде мазать будет всегда**: на 45°-нормалях смешиваются две проекции, и курсы
  кирпича «смазываются». Поэтому в B свод **обязан** использовать swept-UV (B2/B3), а не трипланар;
  «просто включить world-space трипланар» — не решение, а тот же артефакт, что сейчас на колоннах.
* **Курсы на дуге не сойдутся**: если V = длина дуги и текстура тайлится, на замке свода ряды
  смыкаются «веером», а на пяте обрезаются карнизом. Для каменного свода это читается нормально,
  для **прямоугольного кирпича** — нет: нужна отдельная текстура свода с клинчатыми камнями
  (её можно сделать 1 раз в 1–2K и переиспользовать).
* **Арки**: процедурная арка из клиньев (voussoir) даст правильную геометрию, но резной камень
  набора (с фаской и сколами) она не заменит. 29 проёмов — самое заметное место; если хочется
  «как в паке», это единственная часть, ради которой стоит взять A частично.
* **Углы** останутся 90° боксом; без пилястры/шейки угол будет «склеен» из двух текстур.
  Лечится пилястрой-боксом 0.3×0.3 (полдня), но не станет резным углом.
* **UV2/лайтмапы** остаются недоступны (у боксов и heightfield UV2 нет); уровень продолжит жить на
  динамических источниках. Для одного зала 5060 м² это дорого по свету — но это отдельная задача.

## 6. Требования к НОВОМУ паку (если владелец выберет A)

Обязательный минимум:

* **PBR-наборы**: albedo + normal (**OpenGL / Y+**) + roughness (или ORM) + AO, 2K или 4K.
  У текущего пака: albedo + normal + metallicRoughness (G = roughness, B = metal) есть, отдельной
  AO-карты нет; `brickwalls_normal.jpg` — 2048, но какой это стандарт (Y+ или Y−), в паспорте не
  зафиксировано; на глаз (фаска кирпича «выпуклая» при свете сверху) похоже на OpenGL/Y+.
* **Модульная сетка** (2 или 4 м) и **полный набор**: прямая стена, стена с переходом в свод,
  свод/арочный потолок коридора, плоский или рёберный потолок зала, арки/проёмы, столбы, углы
  (внутренний/наружный), плиты пола, лестницы, плинтус/карниз.
  Текущий пак: есть только стена/проём/угол/пол — **5 из 11 позиций отсутствуют**.
* **glTF/GLB** (предпочтительно) или FBX; реальный масштаб в метрах; **UV2 или простая развёртка под
  лайтмапу**. Текущий пак: GLB ✓, масштаб ✓ (4.17 м модуль), UV2 ✗ (ни в одном меше).
* **Стиль**: semi-realistic / stylised-realistic под дварфа (не low-poly flat-colour, не
  фотограмметрия-ультрареализм). Текущий пак по стилю подходит — проблема только в геометрии и UV.
* **Лицензия, разрешающая коммерческое использование, зафиксированная в `res://_docs/licenses.md`.**
  Сейчас файла `_docs/licenses.md` **нет**, а у пака в `PROJECT_FACTS.md` лицензия не указана —
  это надо закрыть до релиза независимо от выбора A/B.
* Дополнительно: триангуляция ≤ ~600 трис/м² (текущий `wall_4m` — 6025 трис на 4×4.86 м ≈ 310/м²
  по площади, но с учётом 1.9 м толщины — 1500/пог. м; для 1168 пог. м это много).

## 7. Рекомендация

**Вариант B+ (B, плюс узкая покупка только под арки/проёмы — по желанию).**

Причины:

1. **Свод в наборе отсутствует физически** — A не «переиспользует имеющийся пак», а требует покупки
   нового кита (свод/потолки/углы/стены в одном стиле) и **полного пере-авторинга** карты 78×46,
   потому что сводчатый модуль задаёт ширину пролёта, а сейчас открытое пространство — одна пещера
   5060 м². Это 6–9 дней и риск для уже работающей логики.
2. **Текущие проблемы — на 80% про UV и плотность, а не про геометрию.** Потолок «как песок» —
   это 2048 px/m на 2K атласе; «кирпич другого масштаба» — 134 против 410 px/m; «скошенные
   кирпичи» — трипланар на цилиндре. Всё это лечится материалами и UV (B1–B3) за ~2 дня и без
   новых ассетов. A эти же ошибки просто спрячет в мешах — и они вернутся на первом же новом
   материале.
3. **Свод процедурно строится дешевле и точнее по стилю**: у нас уже есть heightfield-потолок и
   поле `ceil_h`; заменить константу на профиль пролёта и добавить arc-length UV — это ~2 дня и
   ноль новых зависимостей.
4. **FPS**: A добавляет ~1.75 M трис только на стены; B — на порядок меньше, и остаётся в цели
   60 fps на GTX 1660.

Что взять из A, если бюджет позволяет: **только проёмы/арки** (29 штук) и, при желании, один
«парадный» сводчатый коридор как hero-ассет. Это ~1–2 модели ручной работы или 1 небольшой пак,
и это единственное место, где процедурная арка проигрывает заметно.

**Решение за владельцем.** Нужен один ответ:

* **A** — покупаем/берём пак, пере-авторим уровень, 6–9 дней, максимум качества, риск FPS/сроков;
* **B+** — правим UV/плотность/процедурный свод, 3–4 дня, без новых ассетов, арки остаются
  процедурными (или докупаем 1–2 модели арок — +1 день).

## 10-бис. ПОПРАВКА К §3 И §5 (после реализации)

При реализации обнаружились две ошибки в замерах этого отчёта, обе — в **выводах**, не в методе:

1. **`mat_wall` = 410 px/m, а не 1536.** В `_make_stone(tex, tint, rough, uv, nscale)` четвертый
   аргумент — `uv` (0.4 у стен), а 1.5 — это `nscale`. Отсюда: `mat_wall` 1024×0.4 = **410**,

   верным (134 … 2048), но пара «арка/стена» — 3.1×, а не 11.5×.
2. **`_build_ribs()` — не мёртвый код в смысле «не вызывается никем»**: он не вызывается из `build()`,
   но `mat_cap` реально используется подставками факелов, так что материал живой.

Что от этого меняется в выборе варианта: ничего. Плотность всё равно была разъехана (134 / 410 / 461 /
922 / 2048), и приведение к 512 px/m остаётся первой задачей B. Меняются только конкретные
множители в таблице §3 — фактические значения смотрите в §11.

`mat_wall` 0.4 → **0.5**, `mat_floor` 0.45 → **0.5**, `mat_cap` 0.9 → **0.5**.
Итог: все каменные и кирпичные поверхности ~512 px/м, разброс по уровню с 15× упал до ~1.03×
(единственное исключение — заплатки `dirt` с UV пака 527 px/м, их оставили как есть).

**B2. Стены — модули пака.** `_build_walls()` = `_build_walls_plain()` (кирпичная коробка =
тело стены, материал `mat_brick`) + `_build_wall_veneer()`: на каждую обнажённую грань ставится
модуль `wall_2m` (или зеркальный `wall_2m_b` — по хешу клетки, чтобы кладка не была копипастой).
466 граней = **259 straight + 207 mirrored**, оба через `MultiMesh`, т.е. 2 draw call.
Модуль — тонкая скорлупа без боковых стенок, поэтому коробка остаётся: она закрывает косые углы
и видна только из-за кромки свода и на диагоналях.
Ключевая константа — `WALL_SHIFT := -1.901`: у модуля начало координат на линии гребня свода, а
лицевая кладка на 1.901 м глубже; без сдвига кирпич уезжал внутрь стены. Обшивка дополнительно
смещена на 5 мм вперёд (`WALL_SHIFT + 0.005`), иначе мерцала с гранью коробки.

**B3. Свод-гусёк.** Если набора нет — работает прежний процедурный `_build_cove()`: лента по каждой
обнажённой грани, `COVE_R = 1.0`, `COVE_SEG = 6`, UV **метрические** (u — вдоль стены, v — длина
дуги `COVE_R * ang`), материал `mat_vault`. Это тот самый arc-length UV из плана B: кладка идёт по
кривой с плотностью 512 px/м и не растягивается на изгибе. Обход треугольников — по часовой
стрелке (в Godot это лицевая сторона); первая версия была намотана наоборот и свод был невидим.
Если набор есть (наш случай) — гусёк даёт сам модуль `wall_2m`, а `_arch_open` исключает его
на клетках проёмов, где плечо уже есть у `arch_2m`.

**B4. Потолок.** `_build_ceiling()` теперь пишет **UV в метрах** (`Vector2(p.x, p.z)`) вместо
отсутствующих UV, материал — `mat_vault` = та же кирпичная кладка пака (`_brick_material_uv(0.25)`,
2048 px × 0.25 uv/м = 512 px/м). Раньше потолок брал `stone_wall` и в кадре читался отдельной
плиткой; теперь стена → гусёк → потолок — один камень одного масштаба.

**B5. Колонны.** `_column_material(r, h)` берёт материал `wall_2m` пака и разворачивает его по
цилиндру (`uv1_scale = (TAU*r*0.25, h*0.25, 1)`), `uv1_triplanar = false`. Плинт и капитель переведены
с `mat_wall` на `mat_brick`. 16 опор.

**B6. Проёмы.** `_arched_doorway()` больше не сдвигает арку мировым `−1.07 Z` (на стене вдоль X это
уводило её в кладку и поворачивало на 90°): теперь арка ставится по нормали ближайшей стены
(`_nearest_wall_anchor`) и помечает клетку в `_arch_open`, чтобы по этой грани не строился гусёк.

**B7. Копоть.** Декали сажи больше не лезут на свод: `p.y = clamp(light.y + 0.55, 2.2, WALL_H - COVE_R - 0.55)`.
